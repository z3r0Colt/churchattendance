This runbook and its current CLI describe the single-church baseline. They do not provision a safe shared tenant. Complete MT1–MT6 and update this runbook before onboarding multiple real churches into one project. Do not bypass the current project-reuse protection.

Implementation has passing automated checks: [run 39531708880](https://github.com/z3r0Colt/churchattendance/actions/runs/39531708880), application source `592f350af0f58dd8d06d6657547462234176b14c`. No live projects, billing, DNS, provider sends or production restores have been performed by this change. Real infrastructure acceptance remains a staging gate; a mocked adapter test is not live deployment or backup evidence.

## Private operator workspace

Use infrastructure credentials with deliberate project access, distinct from ordinary church accounts. Application roles do not restrict a cloud infrastructure owner. Prefer short-lived workload identity/ADC; never commit service-account keys. On operator machines, configure ADC and Firebase CLI deployment authorization separately. Keep one central private registry protected by OS permissions and encrypted backup. It must not be hosted on the church origin or stored in church Firestore. Windows operators must restrict the file ACL to named operators; POSIX files must be mode 600. Atomic writes and an exclusive lock serialize changes; after a crash, inspect cloud operations before removing a stale lock.

Create a private registry outside the checkout, such as `.church-operator/registry.json`, with mode 600:

```json
{"version":1,"allowedProjects":["explicit-approved-project"],"churches":{},"releases":{},"audit":[]}
```

Use the fictional examples in `config/deployments` as structure, never as production configuration. Choose the exact church ID, existing project, primary origin, Auth domains, region, time zone, separate storage/backup buckets and dedicated backup service account. This release deliberately supports `us-central1`; changing region or an existing church/project/origin association requires migration planning. Separate each church's Auth, records, credentials, encryption keys, provider accounts and deployment configuration. Demo descriptors require demo projects and loopback endpoints. Unknown descriptor fields, including accidental secret fields, are rejected. Production public branding is validated again with the shared Zod schema before writing.

```sh
npm run operator -- plan --registry /private/registry.json --descriptor /private/church.json --project explicit-approved-project --release FULL_40_CHARACTER_COMMIT
npm run operator -- apply --registry /private/registry.json --descriptor /private/church.json --project explicit-approved-project --release FULL_40_CHARACTER_COMMIT --operator operator@example.test --ticket onboarding-001
npm run operator -- verify --registry /private/registry.json --descriptor /private/church.json --project explicit-approved-project --release FULL_40_CHARACTER_COMMIT --operator operator@example.test --ticket onboarding-001
npm run operator -- status --registry /private/registry.json
```

`plan` performs no mutations or credential lookup and does not print account addresses or secret values. Apply/verify recheck completed steps; a missing resource stays pending and exceptions leave a fixed failure code. Resuming preserves existing users, settings, consent, records and key versions. A remote immutable `deploymentIdentity/church` reservation rejects attaching another church to a used project. Only an empty project can acquire a new reservation. No default project, project creation or billing linkage is performed.

## Infrastructure and enrollment

Before applying, the operator creates the approved Firebase/Identity Platform project, default Firestore database, Storage, Hosting site, recaptcha Enterprise App Check configuration, and deployment/backup identities. Check project quotas and resource availability before promising onboarding. Verify database and bucket ownership and region, Identity Platform MFA, authorized domains and App Check. Grant minimal deployment roles; give the dedicated backup identity only the reads and backup-object creation it needs. Ordinary function identities must not read the backup bucket or recovery wrapping key. Bucket and Secret Manager IAM review is mandatory before staging acceptance.

Apply creates separate missing `PRIVATE_RECORD_KEYS`, `COMMUNICATIONS_CONFIG`, `PORTAL_RATE_LIMIT_KEY` and `RECOVERY_WRAPPING_KEY` secrets in the selected project. It never prints values or replaces disabled historical versions with new encryption material. Preserve old private keys and wrapping-secret versions through rotation and the backup retention window. Restrict recovery bucket/KMS/wrapping-secret access separately from normal records and ordinary app identities. Secret values must never enter the registry.

Initialization creates only missing church settings, public branding and selected service templates. It does not run the sample congregation seed on live projects. Delivery, bulletin and automation delivery remain disabled. Administrator creation uses the chosen email and explicitly approved roles, starting with Admin only unless Session roles were separately approved. No password, verified-email assertion, MFA factor, passkey or assurance session is fabricated. Existing roles are preserved or require reconciliation. Deliver an account-setup/reset link directly through the trusted operator process; do not place it in command output, tickets or a shared default-password document. The administrator must verify the email and complete real MFA/passkey enrollment; existing backend assurance guards still protect records.

Configure DNS/TLS, primary origin, Auth/email-link domains, `PORTAL_ORIGIN`, `STAFF_AUTH_ORIGIN`, `STAFF_AUTH_RP_ID`, calendar UID domain and signed provider callbacks consistently. Pending DNS/TLS stays pending. Changing a passkey RP/origin requires an account/passkey migration and recovery plan; a branding edit cannot do it. Aliases and redirects must be explicitly tested before onboarding, and do not become new passkey origins automatically.

SMS is optional. Assist the church with its own Twilio account/payment, number ownership, registration/verification, signature validation, STOP handling and usage limits. Microsoft Graph credentials and mailbox are per church. Without Graph, outgoing email and email-dependent automation remain unavailable; Firebase Auth emails are not bulk delivery. Provider selection is recorded as disabled/pending, never treated as successful setup because fields were entered. Real delivery requires a separate reviewed staging check and deliberate activation.

## Backup and isolated recovery

Apply can create a daily managed Firestore backup schedule with 30-day retention. The `backups` checkpoint additionally requires a separate bucket with uniform IAM, CMEK and versioning plus verified recovery evidence. Enable versioning on the source Storage bucket and retain noncurrent generations for the recovery window, so cleanup after a Firestore snapshot cannot silently remove a referenced file. Configure lifecycle/retention for auxiliary objects and historical generations to retain 30 days, with any legal hold handled explicitly. Verify IAM, KMS recovery, region and billing before deployment. A billing alert does not stop spending.

`dailyRecoveryBackup` runs at 04:00 UTC under `BACKUP_SERVICE_ACCOUNT`, with `BACKUP_BUCKET`, `PRIVATE_RECORD_KEYS` and `RECOVERY_WRAPPING_KEY`. It requires a ready managed Firestore backup less than 30 hours old, copies current and retained Storage generations under distinct names and verifies checksums, exports Auth identities and password-hash configuration, encrypts the private-record key ring, and saves the exact rules/indexes/Hosting configuration generated by the pinned build. Auth/key/configuration/manifest artifacts use AES-256-GCM with object-path binding; files are protected by the backup bucket's CMEK and IAM. Preserve every wrapping-key version required to decrypt retained snapshots. Auth hash export permission is required; missing recovery material fails the job instead of claiming a complete backup. `backupStatus/daily` and fixed-text job failures make incomplete runs visible without recording narratives or secrets.

Managed Firestore and auxiliary snapshots are captured at different times. Record their actual capture interval; this is not an atomic all-service backup and does not promise zero data loss. Paged XLSX/JSON exports are inspection tools, not a restore protocol. Backup configuration source is generated into the deployed Functions package by `scripts/build-recovery-config.mjs`; build output is ignored by Git.

Before any real restore:

1. Select an explicitly allowlisted, separate recovery project/domain. Deny all public Firestore/Storage access and verify no public Functions, schedules, delivery credentials, webhooks or automations run there. Never restore over the source church.
2. Verify the chosen Firestore backup, auxiliary checksums, configuration release, historical private key ring and matching wrapping-secret version. Verify decryption before importing. Keep decrypted material only in a protected temporary operator environment.
3. Restore the managed Firestore backup using the provider-supported database workflow. If the managed backup cannot restore directly across projects, restore to a new isolated temporary database with deny-all rules, export it to the protected recovery bucket and import into the isolated target. Do not assume a same-project backup supports a cross-project restore. Remove the temporary database only after verified recovery and approval under retention policy.
4. Restore Storage files to the target bucket, preserving paths and verifying checksums. Recover Auth UIDs, account links and supported password-hash parameters through the trusted Admin import process. Import accounts disabled, strip obsolete passkey assurance/grants, and require verified enrollment/recovery before enabling access. Import compatibility for MFA factors/passkeys/provider accounts is a staging drill requirement; never invent replacement factors.
5. Restore the historical private-record key ring to the recovery project's Secret Manager. Preserve document paths for authenticated encryption. Keep recovered public branding/domain/Auth configuration isolated; do not publish source tokens, calendar links or provider credentials. Old message queues, callback receipts, scheduled tasks and workflow side effects must not resume automatically.
6. Validate membership and attendance history, files, account links, authorized decryption and wrong-path rejection. Reapply reviewed rules and test Session/mercy boundaries, including non-Session Admin and unrelated deacon denials. Inspect privacy through supported APIs only after a reviewed recovery deployment; no plaintext fallback.
7. Record measured recovery time and snapshot-to-incident data-loss window. Obtain explicit incident/cutover approval before re-enabling identities, domains, providers or jobs. Preserve the source and recovery evidence until retention decisions are complete.

`recovery-plan` validates a portable encrypted-component manifest and separate target. The portable `captureBackup`/`readBackup` contract and `restore` checkpoint runner support tested recovery adapters. The live managed-backup restore/cutover is deliberately a supervised runbook operation, not a one-click destructive CLI command. The portable manifest and the daily managed-backup bundle are distinct formats; do not feed one into the other.

The CI emulator drill provisions two fictional projects, then actually restores fictional Firestore history, Storage bytes, disabled Auth identities/account links and a key ring into a third project. It decrypts Session/mercy fixtures using the production encryption implementation, rejects wrong document paths, applies real rules, checks client denials and keeps delivery disabled. The drill prints only measured operational results. It does not verify real cloud backup IAM, KMS availability, password/MFA imports, production RPO/RTO or a live disaster cutover.

For offboarding, agree on the export/transfer scope, private-data recipient authority, retention deadline and legal holds. Disable delivery/jobs, revoke staff/portal tokens, factors and calendar links, remove provider credentials and domain access, and provide encrypted exports plus a separate recovery-key handover when authorized. Retain/delete primary data, storage generations, backups and keys according to the agreed schedule; document each completion. Never delete backup keys while a retained snapshot needs them. Deletion/cutover is an explicit operator action, not an automatic consequence of a subscription status.

## Controlled releases and support

Keep versioned release entries in the private registry with full commit, schema/read compatibility, CI result, rollback compatibility, staging/pilot verification and explicitly selected church IDs. An authorized operator records this evidence; a church Admin cannot write the registry or infrastructure. The private registry may also hold external subscription/scholarship status and review date. Do not put service billing, giving, donor or subscription records in congregation collections.

`release-plan` is read-only. `deploy` and `rollback` require project, full commit, named operator and ticket. The deployment driver builds a temporary archive of that exact commit, binds public Firebase/church/origin config, writes server parameters in the temporary tree and deploys rules, indexes, Storage, Functions and Hosting to the selected project. It uses the current managed CLI credentials; it does not use church tokens. Provide the public `VITE_PORTAL_APP_CHECK_SITE_KEY` through the operator runtime. The same source release is rebuilt with each church's trusted public configuration. Temporary output is removed, and command failures are redacted. The Hosting release metadata must match project, church, origin and commit before a version is recorded as verified. Partial deployment keeps the prior verified version and failed target visible; do not blindly retry if a component has a non-reversible migration.

Stage first, verify one pilot, then select each live church deliberately. A release/rollback changes only that church's registry record and project. A Hosting-only rollback is insufficient: restore compatible Functions/configuration/rules/indexes together. Incompatible schemas are rejected. Irreversible data migration needs a separate reviewed migration/recovery procedure and verified backup; these tools do not silently reverse data transformations.

Use named operator identities and fixed support action/ticket records. Obtain church authority and log the access window before exceptional support access to congregation records. Avoid routine inspection of care narratives. Do not paste tokens, email links, private record bodies, account exports or credentials into logs/tickets. Infrastructure ownership is powerful; OS/IAM and human authorization are part of support controls.

Configure uptime checks for launch/public configuration, failed Function/save/job alerts, daily backup age/failure alerts, provider queue errors, storage/secret use and API cost alerts. Monitor counts/error codes and request IDs, never private bodies. The release sets a default ceiling of five instances per Function with concurrency 40; delivery/backup jobs retain tighter instance limits. Set per-project billing budgets, provider limits and abuse/rate limits, and review those ceilings against measured load. These are per-function ceilings, not a service-wide spending cap. Measure actual per-church costs (jobs, secrets, database reads, file versions, backup storage, network and providers) before pricing or capacity promises. Alerts alone do not cap spend.

## Acceptance evidence

Local dependency-free checks cover descriptor rejection, pure dry-run, interrupted/idempotent setup, registry locking/permissions, encrypted component integrity/wrong-key denial, selected release isolation and compatible/partial rollback. CI additionally runs the real emulator provisioning/recovery drills and the existing application/security suites. These are automated evidence only. Real DNS, App Check, MFA/passkeys, provider setup, deployment/rollback, backup access and full recovery must pass staging before Phases 15–17 are accepted for live service.
